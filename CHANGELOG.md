# Changelog

All notable changes to Torvyn are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Torvyn uses the following versioning policy:
- **Major** versions indicate breaking changes to WIT contracts or public Rust APIs.
- **Minor** versions add functionality in a backward-compatible manner.
- **Patch** versions contain backward-compatible bug fixes.
- **Pre-release** identifiers (e.g., `0.1.0-alpha.1`) signal that APIs are not yet stable.

## [Unreleased]

### Added
- Every `torvyn init` template scaffolds a project that runs as generated. A pipeline needs a source and a sink, and a single-component template produced neither end, so a template for one now ships example components for the ends it lacks: `--template transform` generates the transform plus a source and a sink, `--template source` generates the source plus a sink, and `--template sink` the sink plus a source. The user's own component stays at the project root; the examples live under `components/` and are meant to be replaced.
- `torvyn init` refuses a project name that collides with an example component it would scaffold alongside it. The user's component is named after the project, so `torvyn init sink --template transform` would have declared two components called `sink` — a manifest that resolves to nothing, failing at `build` time with the cause far from the effect.
- `TemplateKind::ALL`, and an integration test (`every_template_tests.rs`) that walks it rather than a list written by hand. Every template is scaffolded and driven through `check` and `link`, its printed next steps are checked against what it generated, and the manifest it produces is asserted to declare unique components, connect every flow node to one of them, and grant `stdio:stdout` to the sink that prints. A hand-written list falling behind the enum is how this went unnoticed.
- `torvyn pack` assembles real artifacts. Each declared component (or the one named by `--component`) becomes a gzip-compressed tar at `.torvyn/artifacts/<name>-<version>.torvyn`, carrying the compiled `component.wasm`, an artifact manifest derived from `Torvyn.toml`, the component's WIT contracts, and an in-toto provenance record naming the build tool. Every layer carries its SHA-256 digest, and the artifact round-trips through `torvyn inspect`. The capabilities the manifest records are the union of the `[security.grants]` entries for the flow nodes that run the component.
- `WasmtimeEngine::describe` and `describe_bytes`, plus the `ComponentInterfaces` type: a component's declared imports and exports read from its Component Model type section, without instantiating it. This is what `torvyn inspect` reports.
- `torvyn-packaging` gained `pack_with_manifest`, which packs against a caller-supplied artifact manifest rather than deriving one, and `ArtifactManifest::with_capabilities`.
- The scaffold end-to-end test continues past `run` into `pack`, `inspect`, and `publish`: it asserts each artifact is really gzip-compressed and large enough to hold a component, that `inspect` reports the source's `torvyn:streaming/source`, `lifecycle`, and `types` interfaces, and that the digest `publish` prints is the artifact's actual SHA-256 and matches the copy in the registry. A second test drives `link` over the scaffolded topology and confirms it rejects the same manifest with an edge removed.
- `torvyn-types` crate: shared identity types (`ComponentId`, `FlowId`, `ResourceId`), `ProcessError` enum, `FlowState` state machine, `ComponentRole` enum, and all foundational constants.
- `torvyn-contracts` crate: WIT package definitions for `torvyn:streaming@0.1.0` including `types`, `source`, `processor`, `sink`, and `lifecycle` interfaces. `wit-parser` integration for contract validation.
- `torvyn-engine` crate: `WasmEngine` trait with `WasmtimeEngine` implementation. `ComponentInvoker` trait with typed `invoke_pull`, `invoke_process`, `invoke_push`, `invoke_init`, and `invoke_teardown` methods. Wasmtime resource type integration.
- `torvyn-resources` crate: resource table with generational indices, buffer pool (Small and Medium tiers), ownership state machine (Free to Owned to Transit to Borrowed to Free), copy accounting per element.
- `torvyn-observability` crate: Production-level counters and histograms with pre-allocated metric handles. Basic OTLP trace export. `EventSink` trait for hot-path event recording.
- `torvyn-reactor` crate: minimal single-flow driver, FIFO scheduling, bounded queue with high/low watermark backpressure, demand propagation, cooperative yield.
- `torvyn-linker` crate: two-component topology linking with WIT contract compatibility checking.
- `torvyn-pipeline` crate: pipeline topology construction and validation from TOML configuration.
- `torvyn-security` crate: deny-all-by-default capability model, `SandboxConfigurator` for per-component Wasm sandbox configuration.
- `torvyn-host` crate: runtime binary entry point — startup, pipeline instantiation, graceful shutdown.
- `torvyn-cli` crate: `torvyn init`, `torvyn check`, `torvyn run` commands.
- Benchmark suite: Source-to-Sink latency and throughput measurement, comparison harness for gRPC localhost baseline.
- Real-Wasm benchmark suite (`cargo bench -p torvyn-benchmarks --features real-wasm`): per-element latency and throughput for Source-to-Sink and Source-to-Processor-to-Sink through `WasmtimeEngine` and `WasmtimeInvoker`, a payload sweep across three buffer-pool tiers (8 B / 256 B / 4 KiB / 64 KiB), and pipeline instantiation cost on a warm engine. Every configuration is validated for clean completion, exact copy count, exact copied-byte total, and zero outstanding buffers before it is measured.
- Benchmark regression gate: `check-thresholds` compares criterion's medians against ceilings committed in `benches/thresholds.json` and fails CI on a regression.
- `echo-source` test component accepts a `payload_bytes` field in its `lifecycle.init` config (default 8, preserving the previous behaviour), which is what lets the benchmark sweep payload sizes.
- `torvyn build`: compiles every component the manifest declares with the toolchain for its language and places each artifact at `.torvyn/build/<name>.wasm`, which is where `torvyn run` resolves a flow node's component name to. Rust builds with `cargo component`; other languages set `build_command` on the `[[component]]` entry. The command was documented in seventeen places, including the "Next steps" `torvyn init` prints, and did not exist.
- Component name resolution (`torvyn_pipeline::ComponentIndex`): a flow node's `component = "source"` is now joined to the `[[component]]` declaration that says where that component lives. `file://` and `mock://` references pass through unchanged.
- End-to-end test for the scaffolded path (`--features scaffold-e2e`): scaffolds a project with `torvyn init` and drives it through `check`, `build`, and `run`, asserting the pipeline produces the output its template promises. Wired into CI's `wasm-e2e` job, which already installs the component toolchain.
- Per-element tracing. At `Diagnostic` level the reactor now records a span per component invocation, keyed by the element's origin sequence, into a per-flow ring buffer owned by the observability collector. `EventSink` gains `record_element_span` and `flow_trace_context`, both defaulting to no-ops so existing sinks are unaffected. Below `Diagnostic` the recording path costs one atomic load.
- `StreamElementRef::origin_sequence`: the sequence an element is assigned at the source, carried unchanged through every stage. The per-stream `sequence` is reassigned at each emit site, so it cannot identify an element end to end; this can, which is what lets a trace group a source's, a processor's, and a sink's spans into one element's journey.
- Components can read their flow's W3C trace context: `flow-context.trace-id()`, `span-id()`, and `flow-id()` return the real identifiers the host records the flow's spans under, so a component's own telemetry can be correlated with the host's trace. They previously returned empty strings.
- `HostBuilder::with_collector_config` supplies the observability collector's configuration directly, for callers needing settings the `[observability]` table does not expose.
- `FlowRecord::stages` records each stage's `ComponentId`, node name, and role, so a report can name a component rather than printing its positional id.
- WIT contract definitions: `torvyn:streaming@0.1.0` package with split `buffer` / `mutable-buffer` resource model.
- Project scaffolding: `torvyn init` generates component projects with WIT contracts, Cargo configuration, and starter implementations.
- CI pipeline: build, test, lint (`clippy`), format check (`rustfmt`), MSRV verification, benchmark regression detection.

### Changed
- `torvyn init` prints next steps that suit the template it just ran. The `empty` template scaffolds no components on purpose, so it no longer advertises `torvyn build` and `torvyn run`; it says what to add instead.
- The error for a manifest with no flow names the project's own components and shows the `[flow.main]` block to add, wired to those components. It previously said "Add a [flow.*] section" — which tells a reader who knows the syntax something they knew, and everyone else nothing. `run`, `link`, `trace`, and `bench` share one implementation of it.
- Published performance numbers in `README.md` and `benches/README.md` are now measured on the real-Wasm path. The previous figures came from the mock-invoker path, which executes no WebAssembly and moves no payload bytes; they are retained, relabelled as the runtime's overhead floor, and no longer presented as the cost of running a pipeline.
- Span ids are derived from `(flow_id, component_id, element_sequence)` rather than generated from the current nanosecond. The previous generator seeded itself from `SystemTime::now`, so two spans created within the same nanosecond received identical ids — on the hot path, not a hypothetical. Derivation is also allocation-free and reads no clock.
- The gRPC comparison (`comparison/grpc_comparison.rs`) gained a real-Wasm arm carrying the same 256-byte payload as the gRPC arm, making it a like-for-like measurement. Its criterion groups were renamed to `torvyn_vs_grpc_latency` and `torvyn_vs_grpc_throughput`, with each arm named for what it actually executes.

### Deprecated
- Nothing yet.

### Removed
- `torvyn init` no longer offers the `filter`, `router`, and `aggregator` templates. See the Fixed section: they scaffolded components that compile and cannot run.

### Fixed
- Seven of the eight `torvyn init` templates scaffolded a project whose own printed next steps could not be completed. `init` ends by telling the user to run `torvyn check`, `torvyn build`, and `torvyn run`; every template except `full-pipeline` generated a manifest with components and no flow, so step three failed with "No flow defined in manifest" and told the user to hand-write a section into a file generated seconds earlier. `link`, `trace`, and `bench` failed the same way.
- The `source` and `sink` templates could not compile. Both imported `LifecycleGuest` and never implemented it, and the `data-source` and `data-sink` worlds export `lifecycle` — so `export!` failed to satisfy the world. Neither template had ever been built by a test; only `full-pipeline` was.
- The `transform` template could not compile either. Its pass-through body returned `ProcessResult::Emit(input)`, but `input` is a borrowed `StreamElement` and the variant takes an owned `OutputElement`. The pass-through now reads the payload, copies it into an allocated buffer, and emits that, which is what the borrow/own split in the contract requires.
- `torvyn init --template filter`, `--template router`, and `--template aggregator` scaffolded components the runtime cannot execute. Each shipped its own `filter.wit` / `router.wit` / `aggregator.wit` — interfaces present in no contract the engine binds — so a scaffolded filter compiled, exported `torvyn:streaming/filter@0.1.0` and nothing else, and was then refused at instantiation: `detect_world` tries `data-source`, `managed-transform`, `data-sink`, and `transform`, and none of them match. The scheduler compounded it by dispatching `Filter` and `Router` stages as `StageAction::ProcessElement`, which calls a `process` export those components do not have. The three templates are withdrawn until the Phase 1 `torvyn:filtering` and `torvyn:aggregation` interfaces make them runnable; the roles remain modelled across the reactor, pipeline, and linker crates.
- `torvyn pack` wrote a 57-byte JSON stub named `<component>.tar` and reported "Packed". `tar -tf` called it an unrecognized archive format, and `torvyn inspect` could not read it. The `torvyn-packaging` crate — layers, digests, provenance, OCI media types, and its own tests — was complete and simply not called. `pack` now uses it, and refuses to write anything until every selected component has been built, naming all the unbuilt ones at once instead of failing on the first.
- `torvyn link` failed on every project with "invalid type: map, expected a string in `edges.from`". It parsed `Torvyn.toml` with a private schema that had drifted from `torvyn_config`'s: the real manifest writes an edge endpoint as `{ node = "source", port = "output" }`, and the private one expected `"source.output"`. It now uses the canonical types, resolves each node's component through `torvyn_pipeline::ComponentIndex`, infers roles from the interface path, and passes the node's `[security.grants]` capabilities to the linker — which it previously supplied as an empty vector, so the capability half of the check never ran.
- `torvyn doctor` reported every tool as "NOT found" on every machine, including the toolchain that had just built it. `check_command_version` ran `args[0]` as the program name while its only caller passed the program as `name` and `["--version"]` as `args`, so each check tried to execute a binary literally named `--version`. It also now treats a non-zero exit as a failure: spawning successfully proves a binary exists, not that it works.
- `torvyn inspect` reported `exports: []` and `imports: []` for every component and every artifact — for a contract-first runtime, the one thing inspection exists to show. Both lists are now read from the binary's Component Model type section. A bare `.wasm` no longer claims version `0.1.0`, which was invented; it reports `unknown`, since a bare binary carries no manifest.
- `torvyn publish` printed a digest computed by hashing the artifact's *path* with `DefaultHasher` and labelling the 64-bit result `sha256:`. Two different builds written to the same path digested identically, and the value matched nothing `sha256sum` would produce. It is now the real SHA-256 of the artifact's bytes, verified against the copy written into the registry. Publishing to a remote registry reported success with the literal digest `sha256:placeholder` while pushing nothing; it now fails with an explanation. With no `--artifact`, the search for the latest artifact looked only for `.tar` files and so found none of what `pack` produces.
- `torvyn bench` reported zero throughput, zero copies, and zero latency for every flow that terminates — which is every example and the scaffolded project — and presented it as a successful benchmark. A finite flow finishes in milliseconds, long inside the default two-second warmup, so the measurement window that followed observed a flow that had already stopped. Both phases now watch the flow's state and end as soon as it reaches a terminal state; the report covers the run that actually happened and carries a note explaining that there was no sustained load to measure. A benchmark of the scaffolded project takes 2.4 s instead of 12 s and reports real figures.
- `torvyn pack --include-source` was accepted and unread. WIT contracts are always packaged, so the flag now warns that it has no effect rather than implying the artifact would differ without it.
- The documented first-run path did not work. `torvyn init` scaffolds a project and prints three next steps; every one of them failed. `torvyn build` did not exist. `torvyn run` could not resolve a flow node's component name, reporting "unsupported component reference scheme in 'source'" — naming the component as though it were a malformed URI — because the manifest's `[[component]]` declarations were never consulted. All four shipped examples failed the same way; three now build and run, and `token-streaming` is marked as needing the Phase 1 filtering and aggregation interfaces.
- The scaffolded WIT had drifted from the contract crate: its `data-source` world no longer exported `lifecycle`, so the host declined every generated source with "not a data-source", and `types.wit` differed by 182 lines. Templates now embed the canonical `torvyn:streaming` contract with `include_str!`, so a scaffolded project cannot diverge from the runtime it will run against. The source and sink templates implement `lifecycle` as their worlds require.
- Scaffolded components carried no `[workspace]` table, so creating a Torvyn project inside another cargo workspace produced components cargo refused to build, and no `[package.metadata.component.target]`, so `cargo component` looked for WIT in `wit/` alone and missed `wit/torvyn-streaming/`.
- `torvyn check` reported "All checks passed" having parsed zero of a project's WIT files: it looked only at `<project>/wit` and never at the per-component directories a multi-component project uses. It now checks both, and prints the warnings it collects — a check that suppressed its own warnings is how "0 file(s)" read as success.
- The scaffolded sink prints what it receives but was granted no capability to do so, so its output vanished into a deny-all sandbox. Templates and examples now grant `stdio:stdout` to the nodes that print, and nothing else.
- `torvyn run` accepted `--limit`, `--input`, `--output`, and `--config` and ignored all four. They now exit with an explanation. `--log-level` is documented as not yet wired, since the CLI installs no log subscriber.
- `torvyn trace` reported a hardcoded result of all zeros — zero elements, zero latency, zero copies, no spans — after successfully running the pipeline, and did so without an error or warning. It now reports the run: per-element spans grouped into each element's path through the pipeline, with real durations, copy counts, and backpressure figures. It also no longer starts the traced flow twice (it called `start_flow` and then `TorvynHost::run`, which starts every flow in the manifest).
- Per-component processing time was recorded as zero for every invocation of every component. `FlowDriver::execute_stage` passed `start.elapsed()` and `(start + duration).elapsed()` to `EventSink::record_invocation`, which measure time *since* an instant rather than points in time; the resulting `end_ns` was smaller than `start_ns`, so every sink computing `end_ns - start_ns` saturated to zero. Both are now absolute epoch timestamps, derived from a per-flow anchor so the hot path reads no wall clock. The bucketed percentile masked this — a histogram of nothing but zeros still reports a non-zero p95 by interpolating inside its first bucket — so the regression tests assert on the mean.
- `torvyn trace --show-buffers` was accepted and silently ignored, along with `--limit`, `--trace-format`, `--output-trace`, and `--show-backpressure`. The latter four now work; `--show-buffers` exits with an error explaining that the runtime does not retain payload bytes after an element is consumed.
- gRPC benchmark baseline: sockets accepted by the in-process echo server kept Nagle's algorithm enabled, because `serve_with_incoming` bypasses tonic's own socket configuration. Combined with the client's delayed-ACK timer this stalled every unary round trip until the timer fired — a flat ~41 ms per call on Linux CI runners, against ~53 us on macOS. The baseline was measuring a kernel timer rather than gRPC's transport cost, and the CI benchmark job timed out before finishing. `TCP_NODELAY` is now set explicitly on both ends.
